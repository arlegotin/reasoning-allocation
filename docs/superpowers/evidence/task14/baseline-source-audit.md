## Implementation behavior and fidelity risks

### Labassi B7

[Paper section 5.4](https://arxiv.org/html/2210.16934v1#S5.SS4) describes highest-ranked selection followed by estimate after two feasible solutions. Its teacher follows an optimal solution; the paper reports V100/Xeon Gold 6126 hardware, which is reported hardware rather than a proven minimum requirement.

The pinned code's counter is more specific. [GNN comparator lines 337–428](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/node_selection/node_selectors.py#L337) initializes `n_primal=2`, `best_primal=inf`, and `primal_changes=0`. On each comparison it first checks whether the counter has already reached two; otherwise it observes the current best solution, reverses objective sign for maximization, and increments only on a strict incumbent improvement. The comparison observing the second improvement still uses GNN scores; later comparisons use estimate comparison. Multiple improvements between comparisons can collapse into one observation. Scores are cached by SCIP node number. The default inherited `nodeselect` selects `getBestNode()` for the `dummy` selection policy. Therefore a raw solution counter, a handoff at an event callback, or a priority change to native estimate would each be a behavior change, unless separately justified and labelled. The common anchor can count as the first observed improvement; an anchor-aware adaptation must remain distinct.

[Teacher lines 174–233](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/node_selection/node_selectors.py#L174) checks ancestor branching bounds against a known optimum, preferring a node containing it. Both containing it uses depth comparison; neither uses estimate. [Recorder generation lines 45–70 and 74–106](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/node_selection/behaviour_gen.py#L45) saves only discriminating comparisons, then reverses their choice to obtain additional examples; it reads paired `.sol` files. Faithful teacher reproduction therefore includes prior optimal solves, that sampling behavior, and their resource cost.

[Graph recorder lines 323–351 and 424–488](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/node_selection/recorders.py#L323) constructs original-model bipartite graphs and recursively changes branching bounds; some paths for newly added constraints are commented out. Variables have six features, constraints four, edges coefficients; infinite original bounds use finite replacements. This is not interchangeable with a modern dynamically extracted LP graph. [Model lines 45–99 and 149–211](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/learning/model.py#L45) uses a 32-dimensional initial embedding and three GraphConv stages, then norm-based graph scores and sigmoid pairwise score differences. [Training lines 21–33](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/learning/train.py#L21) specifies BCE/Adam. Exact tensor and live-feature parity remain unperformed.

### Mattick B8

[Selector initialization lines 114–134](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/SelectTree.py#L114) starts a step counter at zero and maps steps 0–250 to every-step inference and steps 250–1000 to every tenth step; overlapping range evaluation keeps step 250 in the first range. [Selection lines 142–208](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/SelectTree.py#L142) increments the counter first and, at `step>=750`, lowers the custom selector's standard priority to zero and returns the best-bound node. Thus the source handoff occurs on call 750, with learned inference only through 749. Other noninference calls return best-bound; every 50 calls it prunes stored tree entries. The eventual native selector after priority reduction depends on the actual priority configuration. The comparator itself is lower-bound ordering.

**Version discrepancy:** both [2023 arXiv v1 section 4.2](https://arxiv.org/html/2310.00112v1#S4.SS2) and [2024 arXiv v2 section 4.3](https://arxiv.org/html/2310.00112v2#S4.SS3) describe inference at each of the first 250 selections, then every tenth for the next 750, followed by classical selection: apparently 1000 selections total. V2 also describes a different cutoff for longer-budget evaluation. This differs from the published repository's 750-call guard. Preserve the pinned source regime required by section 8; record the paper regime separately and settle which publication/version is targeted before calling it paper-faithful. The discrepancy is an unresolved regime choice, not performance infeasibility.

[TreeList probability routines, lines 66–104 and 182 onward](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/TreeList.py#L66) implement candidate distributions from retained tree representations. [Sampling lines 16–29](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/SelectTree.py#L16) filters to live node IDs, sorts IDs, and samples a categorical distribution; this is not a deterministic best-score selector. [PPO configuration](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/confs/training_scheme/PPO.yaml#L1) declares clipped PPO, entropy/value coefficients, gradient clipping, and 16 update epochs.

## Plausible minimum CPU reproduction path — not run

The following is a proposed sequence, contingent on resolving author-code/asset permission and building isolated environments. It is not a measured hardware requirement, parity result, or reproducible experiment already completed.

1. Establish component and asset reuse terms and record notices. Pin source, solver, compiler, numerical dependencies, and CPU thread counts independently of the main project. Use an original x86-64 environment where old dependency support is easiest to obtain; ARM64 common-build work is a separate adaptation.
2. For Labassi, start with Python 3.9, matching SCIP 7.0 and the 3.0.2 fork, then a mutually compatible CPU Torch/PyG set. Do not execute `setup_env.sh` directly: its first commands delete an environment and its active installs are GPU packages. Source scripts explicitly support CPU and one worker: [main.py CLI, lines 19–47](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/main.py#L19), [teacher CLI, lines 142–172](https://github.com/ds4dm/learn2comparenodes/blob/da802e8d1e6687ca7b5593e3e0cad42eb4499942/node_selection/behaviour_gen.py#L142). After permissions and inputs are resolved, a one-instance inference entry is `python main.py -device cpu -n_cpu 1 -n_instance 1 -nodesels gnn_dummy_nprimal=2 -problem GISP -data_partition test`. This still requires the correct checkpoint and authorized instance. It does not reproduce teacher/training. Generate tiny disjoint training/validation instances with proven optima; run the discriminating teacher and then CPU training with small batches. The committed tree exposes test/transfer files and model weights, but no saved teacher `.pt` corpus or ordinary train/valid instance directories was established. Do not infer the downloaded weights themselves are licensed from wrapper MIT.
3. For Mattick, first reproduce the Python 3.10/PySCIPOpt 4.3/SCIP 8.0.3 CPU path with compatible numerical packages and repaired explicit extension linkage. [config.yaml lines 4–21](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/confs/config.yaml#L4) already says CPU, 19 features, width 512, depth 2, one layer and eight rollouts. [main rollout lines 70–94](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/main.py#L70) explicitly selects CPU and uses 45-second limits. Thus GPU removal alone is not an architectural rewrite. ArXiv v2 reports all training/experiments on a Ryzen 7 5800X3D CPU, approximately six hours; it does not establish minimum RAM or minimum processor. Generate disjoint tiny inputs and the required `info.csv` manifests; [problem_maker.py lines 20–83](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/problem_maker.py#L20) provides generation/median selection but initially evaluates 256 candidates, so the full default generator is not a tiny smoke recipe. [main training lines 185–225](https://github.com/MattAlexMiracle/BranchAndBoundBisim/blob/199ae6e5c42155aa528951cb93bec9482e03545e/main.py#L185) requires absent `training_data/info.csv`, `eval_data/info.csv`, output directories, Ray and W&B. Limit rollout workers explicitly because `Pool(8)` is hardcoded; merely reducing `env.num_rollouts` does not change the pool. Disable network logging locally and preserve the original width/depth for parity; a reduced-width model is only a smoke approximation. `python main.py device=cpu env.num_steps=1 env.num_rollouts=1` is a prospective short entry after those fixes and inputs, not a working command proven by this audit.
4. For both, compare synthetic forward tensors, exact feature arrays, stochastic action distributions where applicable, and boundary handoffs before any training comparison. Include no-incumbent, incumbent-improvement, anchor, maximization, degenerate/empty-feature, and root-solved cases. Confirm all live selections are retained frontier nodes and verify tiny optima against native SCIP. Then measure CPU time, peak memory, teacher/generation, graph extraction and preprocessing, with seeds and thread settings. Neither CPU feasibility nor resource cost can be inferred from this static audit alone.
5. Only after original-regime evidence, port to Python 3.12.9/ARM64/PySCIPOpt 6.3.0/SCIP 10.0.2. Record all API, import, numerical, feature, solver-setting, candidate and handoff changes. Compare tensor and live-feature parity; run common-build correctness and prospective validation. Keep original, adapted, and approximate regimes separate.
